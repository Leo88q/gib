# ГИБ: эксплуатация и реагирование

Статус на 05.11.2026. Это рабочий регламент для прототипа, а не описание
готового к запуску сервиса. Production API намеренно закрыт заглушкой 503;
регламент описывает, как понять, что происходит, и что делать, но не снимает
блокеры запуска.

## 1. Три вопроса, три эндпоинта

Смешивать их нельзя: ответ «мёртв» и «болен» требует разных действий.

| Эндпоинт | Что отвечает | Код | Действие при отказе |
|---|---|---|---|
| `GET /api/health` | Процесс жив и выполняет код | всегда 200 | Перезапустить процесс |
| `GET /api/ready` | Можно ли принимать запросы: состояние читается, база доступна | 200 / 503 | Убрать из балансировки, **не** перезапускать |
| `GET /api/metrics` | Числа нагрузки в формате Prometheus | 200 с токеном, 401 без | — |

`/api/health` **не читает диск и не ходит в базу**. Если бы он зависел от базы,
«мёртвый» и «больной» стали бы неразличимы, и перезапуск приходил бы туда, где
он не помогает.

Служебные маршруты открыты и в production, даже когда весь пользовательский API
отвечает 503: иначе невозможно ответить, жив ли сервис, и заглушку пришлось бы
снимать вслепую. Это проверяется тестом `test:observability-prod`.

## 2. Что означают статусы готовности

```json
{ "status": "ready" | "degraded" | "not_ready", "ready": true, "checks": [ ... ] }
```

- **ready** — всё настроено, включая оплату и бота.
- **degraded** — принимать запросы можно, но часть возможностей выключена
  (нет ключей оплаты, нет токена бота). Игра работает; оплата и сообщения — нет.
  Это нормальное состояние прототипа, а не авария.
- **not_ready** — нельзя работать: состояние не читается или файл базы
  недоступен. Ответ 503, балансировщик должен убрать инстанс.

Проверки никогда не пишут в хранилище: проверка готовности не имеет права менять
данные.

## 3. Метрики

Формат Prometheus на `GET /api/metrics` с заголовком
`Authorization: Bearer <GIB_METRICS_TOKEN>`.

Без токена — 401 и **ни одного имени метрики**: открытые метрики в интернете
раскрывают нагрузку и состояние сервиса. Токен короче 16 символов не принимается.

Что есть:

- `gib_uptime_seconds` — время работы процесса;
- `gib_http_<route>_total`, `_errors_total`, `_duration` — только на маршруте
  сессии (`session.info`, `session.command`): там же видны 5xx;
- `gib_ratelimit_allowed_<scope>_total`, `.._blocked_..` — по областям, не по
  владельцам;
- `gib_readiness_checks_ok_total`, `.._failed_total`,
  `gib_readiness_degraded_checks` — состояние готовности;
- `gib_health_checks_total`, `gib_metrics_scrapes_total`;
- `gib_check_<id>_ok_total` / `_failed_total` для обязательных проверок.

Ограничения, о которых надо помнить:

- метрики живут **в памяти процесса** и обнуляются при перезапуске;
- они **не** распределённые: при нескольких инстансах у каждого свои числа;
- кардинальность ограничена 500 именами; отказы записываются в
  `gib_metrics_dropped_total`, а не теряются молча;
- числа не заменяют журнал: метрика говорит «медленно», лог — «почему».

## 4. Логи

Одна строка JSON на событие, в stdout (ошибки — в stderr):

```json
{"ts":"2026-11-05T10:00:00.000Z","level":"error","event":"request_failed","route":"session.command","error":{"name":"Error","message":"..."}}
```

Уровень задаётся `GIB_LOG_LEVEL` (`debug` / `info` / `warn` / `error`).
По умолчанию `info`, в тестах `warn`.

**Чего в логах не будет никогда:** `initData`, заголовков авторизации, токенов
ботов, ключа резервных копий, имени и возраста ребёнка, содержимого ответов и
отметок чувств. Вырезание происходит на выходе, а не по договорённости
вызывающих: если в поле попадёт секрет, он будет заменён на `[redacted]`.
Токены и подписи вырезаются даже из свободного текста. Это проверяет
`test:log-redaction`.

Идентификатор владельца в логах по умолчанию отсутствует. Если нужен для
отладки — `GIB_LOG_OWNERS=1`; тогда пишется короткий необратимый отпечаток,
не сам ID.

## 5. Реагирование: базовые случаи

### Готовность `not_ready`, живость 200

1. Прочитать `checks` в ответе `/api/ready` — там названа причина и путь файла.
2. Проверить, на месте ли файл базы и есть ли к нему доступ у процесса.
3. Если файл повреждён — восстановление по `docs/operations.md` ниже и
   `npm run restore:check` (см. раздел 6).
4. Перезапуск сам по себе не поможет: проблема в данных, а не в процессе.

### Живость не отвечает

Процесс завис или упал. Перезапустить. Если повторяется — смотреть stderr и
последние строки лога: там будет `request_failed` с маршрутом.

### Метрики без токена отдают 401 дежурному

Токен не задан или не совпадает. Проверить `GIB_METRICS_TOKEN` (не меньше
16 символов) в окружении и заголовок запроса. Токен **не** хранится в коде и не
пишется в лог.

### `gib_ratelimit_blocked_*` быстро растёт

Кто-то упирается в лимит. Лимит по процессу, не распределённый: при нескольких
инстансах реальный предел умножается на их число. Если рост из-за одного
владельца — это защита; если из-за всех — проверить, не режется ли нормальная
нагрузка, и поднимать лимит осознанно.

### `http_session_command_errors_total` растёт

Смотреть лог `request_failed`: там маршрут и текст ошибки, без тела запроса.
Не пытаться воспроизводить на реальных детях: сначала на демо-данных.

## 6. Резервные копии и восстановление

Регламент восстановления описан в коде (`lib/restore-plan.ts`) и проверяется
тестами `test:restore-plan` и `test:restore-drill`.

Коротко:

1. Остановить сервис.
2. Сохранить текущий файл базы и его `-wal` / `-shm` рядом, ничего не удаляя.
3. `npm run restore:encrypted -- <backup.gib> <new.sqlite>`
4. `npm run restore:check -- <new.sqlite>` — отчёт прямо скажет, можно ли
   подключать копию.
5. Подключить только после успешной проверки; прежний файл оставить для отката.
6. Проверить приёмку: кабинет, одна миссия, совпадение наград.

Автоматического подключения восстановленной базы нет намеренно: приёмку делает
человек.

## 7. Что остаётся за пределами этого регламента

Это не сделано и не должно выглядеть сделанным:

- **нет** распределённого rate limit (счётчики в памяти процесса);
- **нет** экспортёра метрик как отдельного процесса и **нет** настроенного
  сбора (Prometheus/Grafana) — есть только формат;
- **нет** алертов, дежурных графиков и порогов;
- **нет** трассировки запросов между сервисами;
- **нет** ротации ключей и автоматической очистки старых копий;
- **нет** нагрузочных и независимых security-тестов;
- секреты пока передаются через переменные окружения; управление ими
  (хранилище секретов, доступ, ротация) не сделано;
- полевое тестирование с реальными семьями и специалистами не проводилось.

Перечисленное относится к коммерческой готовности и блокерам запуска, а не к
этому регламенту.
