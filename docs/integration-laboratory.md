## Локальные соединители (эксперимент, не подключены к игре)

`lib/experiments/local-connectors.ts` и `npm run lab:integrations -- ...` позволяют тестировать отдельно:

- `pocketbase`: SDK читает первую страницу строго синтетической общедоступной коллекции `gib_lab_stories`, с проверкой ID и тестовых заголовков. Это не подключённый редактор и не источник прогресса. Игра по-прежнему использует свои каталоги и хранилище. SDK 0.28.1 MIT; репозиторий PocketBase на GitHub архивирован и сообщает о переносе на `ganigeorgiev.com`. Версию сервера и правила доступа нужно согласовать и проверить отдельно.
- `lrs`: отправка одного фиксированного синтетического xAPI statement в `/xapi/statements` с Basic-auth и заголовком 1.0.3. Это не клиент полной спецификации xAPI и не подключённый LRS; выбран кандидат [Yet SQL LRS](https://github.com/yetanalytics/lrsql), Apache-2.0.
- `umami`: отправка одного фиксированного синтетического события в `/api/send`; SDK/трекер на детском экране не устанавливается. [Umami](https://github.com/umami-software/umami) MIT, конфигурация, политика доступа и удаления ещё не определены.

`GIB_LAB_BASE` принимает только HTTP на числовом loopback с явным портом и без пути, логина и редиректов; production запрещён. Для LRS ключи передаются через `GIB_LAB_LRS_KEY` и `GIB_LAB_LRS_SECRET` только в окружении, не в файлах или аргументах; для Umami ID синтетического сайта — `GIB_LAB_UMAMI_SITE`. Например, `npm run lab:integrations -- fsrs` не требует сервиса. Для других режимов поднимите отдельно изолированный тестовый экземпляр, не размещайте его публично и используйте только фиктивные данные. Секреты не коммитить.

HTTP-мок проверяет форму запросов, отказ внешних URL, редиректов и production-блокировку, а также отклонение неверной квитанции LRS. Дополнительно SDK и каталог проверены с настоящим изолированным PocketBase **0.22.20** через локальный HTTP: синтетическая запись восстанавливалась после рестарта; анонимная запись, изменение, удаление и просмотр отдельной записи отклонялись; неверный контент, дубликат и более 50 записей отвергались. Бинарник для этого эксперимента взят из стороннего npm-пакета `pocketbase-linux-amd64@0.22.20-4`, не был сверен с официальным релизом и затем удалён вместе с тестовой БД. Это старый сервер и не проверка актуального PocketBase или его безопасности. В среде Docker отсутствует, официальные release-assets недоступны; Yet SQL LRS не запускался. Позже Ralph и Umami 3.4.1 проверен отдельно на фиктивных данных, см. ниже. До подключения к реальным данным необходимы установка и интеграционные тесты сервисов, конфигурация доступа и удаления, моделирование угроз и правовая оценка. Наличие идентификатора сайта или события даже без содержимого может повлечь обработку данных, в том числе IP и user-agent; никакой сбор не включён.

## Повторение теста PocketBase 0.22

Только на изолированном одноразовом сервере с пустой БД и фиктивным администратором: задайте `GIB_LAB_BASE` (например, `http://127.0.0.1:8079`), `GIB_POCKETBASE_DISPOSABLE=1`, `GIB_LAB_ADMIN_EMAIL` и `GIB_LAB_ADMIN_PASSWORD` в окружении. Запустите `npm run setup:pocketbase-lab-real`, затем `npm run test:pocketbase-lab-real -- prepare`. Перезапустите сервер и выполните `npm run test:pocketbase-lab-real -- resume`. Setup отказывается работать с существующей коллекцией; тест временно создаёт и удаляет только синтетические записи. После теста удалить одноразовую БД. Пароли не передавать через исходный код или репозиторий, а production и реальные профили не использовать. Это тест legacy API 0.22, а не инструкция по развёртыванию или гарантия безопасности.

## Отдельное SQLite-хранилище автомата дня

`lib/day/day-flow-sqlite.ts` — экспериментальный самостоятельный репозиторий, **не подключённый к игровому API, экрану, существующей БД, экспорту и удалению профиля**. Каждая операция выполняется под `BEGIN IMMEDIATE`; повтор идентичного operationId возвращает текущее состояние без второго перехода, другой запрос с тем же ID или устаревшей версией отклоняется. Идентификатор владельца проверяется при чтении и обновлении, но внешний вызывающий код обязан аутентифицировать владельца и получать выбор историй от сервера. Создание не ограничивает количество потоков на профиль. Метод удаления работает только в этом отдельном хранилище.

Снимки проверяются воспроизведением ограниченного набора квитанций через XState, включая последовательность версий, допустимые переходы, карточку, результаты и точную схему. Лишние поля (включая чувства) отклоняются, повреждение не перезаписывается. Тест на фиктивных данных проверяет четыре процесса с одновременным повтором, конкурирующие переходы, перезапуск экземпляра, откат при ошибке записи, повреждение, владельца и удаление. SQLite используется на одном локальном диске; это не PostgreSQL, не распределённая транзакция и не production-интеграция. До использования в приложении нужны привязка к сессии и наградам в одной транзакции, версии контента, полномочия, экспорт/удаление, миграции и HTTP/WebView-тесты.

### Игровой сегмент XState

В новых сессиях `storyChoice` с практикой `runtime.storyFlow` сохраняет этап выбора, истории и практики вместе с состоянием сессии, а переход и награда применяются в одной транзакции текущего хранилища. При одной карточке выбор не показывается; старые runtime без маркера продолжают работать по старому пути. Валидатор сверяет этап с планом и индексом. Значение `reflection` в этом внутреннем сегменте лишь означает, что практика завершена или пропущена; сам экран итога остаётся локальным. На фиктивных SQLite-данных проверены HTTP, два рестарта после истории/практики, параллельные повторы, единичная награда и удаление; PostgreSQL-репозиторий остаётся экспериментальным, а JSON не обеспечивает межпроцессную атомарность.

Примечание к тестовой инфраструктуре: в одном запуске общего набора `test:postgres-cli` завершился ошибкой `PGliteSocketServer` при закрытии уже закрытого PGlite (`isInTransaction`); отдельный повтор и последующий полный `npm test` прошли. Это наблюдаемая нестабильность завершения тестового сокета, не подтверждение корректности или некорректности production PostgreSQL. Требуется устранить гонку и повторить проверку.

Исследование нестабильности тестового PGlite-сокета: в установленном `pglite-socket` `stop()` вызывает асинхронный `detach`, но не ожидает его, а обработчик `close` также вызывает `detach` асинхронно. Публичный `stop()` сам по себе не гарантирует завершение всех таких операций до `db.close()`. Причина согласуется с наблюдаемой ошибкой.

**Исправление (06.11.2026).** Добавлен `scripts/pglite-socket-shutdown.ts`: после `stop()` он ждёт, пока база выйдет из транзакции и останется спокойной две проверки подряд, и только затем отдаёт управление тому, кто вызывает `db.close()`. Ожидание ограничено 5 секундами; по истечении тест не падает, но печатает предупреждение — инфраструктура не должна валить проверку продукта. Помощник подключён во все три теста с сокетом. Новый `test:pglite-shutdown` ставит условие гонки детерминированно — открытая транзакция и закрытие без ожидания.

**Честная оговорка о доказательстве.** В этом окружении исходное падение воспроизвести не удалось: три попытки со старым поведением (`stop()` и сразу `close()` при открытой транзакции) прошли, потому что `detach` успевает раньше, чем планировщик отдаёт управление. Значит, исправление устраняет известную причину и фиксирует порядок операций, но не подтверждено наблюдением «падало до, не падает после». Тесты остаются экспериментальными в том смысле, что их нельзя считать доказательством отсутствия гонки.

### Игровой ink первой недели

Новые сессии с выбором карточки фиксируют компилированный ink для возрастного варианта каждой из 11 историй первой недели. Сервер исполняет снимок для текста, вариантов и ответа; JSON снимка не отправляется в игровом item. Старые снимки без ink читаются прежним способом. ### Дневная схема v2

Версия 2 включается для новых сессий с `journey: true` всех 60 дней, включая повтор; активные v1 не мигрируются. ### Синтетическая очередь xAPI и повтор после потери ответа

`lib/experiments/lrs-synthetic-outbox.ts` — отдельный лабораторный прототип, не подключённый к игре: принимает только автоматически созданные UUID и формирует один фиксированный вымышленный actor, verb и activity. Ни пользовательские данные, ни токены не сохраняются. Строка очереди содержит только ID, технический статус, попытку, время и временную аренду. SQLite WAL использует `BEGIN IMMEDIATE`; `reserve` выдаёт одну аренду, истёкшая может быть перехвачена, а устаревший работник не может подтвердить новую аренду.

Доставка использует `PUT /xapi/statements?statementId=<UUID>` с одинаковым ID и телом. Согласно предполагаемой семантике xAPI, при совместимом LRS повтор идентичного statement должен возвращать 204, конфликтующий — 409. `204` завершает запись, `409` и постоянные 4xx/неожиданные 2xx прекращают автоматические повторы; неизвестный результат, 408, 429 и 5xx оставляют запись для повтора с ограниченным backoff. Стабильный ID помогает избежать дубля после потерянного ответа только если конкретный LRS соблюдает эти правила. Повтор самого `enqueue` создаёт новый ID; транзакционного связывания с игровым событием нет. Для Umami этот механизм не применён: другого API и гарантированной дедупликации в нём не выявлено.

`npm run test:lrs-synthetic-outbox` проверяет **HTTP-мок**, включая запись на сервере с потерей ответа, рестарт SQLite, повтор, 409, 401/429/503, редирект, четыре процесса, истекшую аренду и чужую БД. Он также проверяет оба этапа `test:lrs-lab-real` против мока. `test:lrs-lab-real -- prepare` / `-- resume` подготовлены для отдельного настоящего LRS с перезапуском между этапами: фиксированный PUT, GET, идентичный повтор и конфликтующее тело. Для запуска требуются `GIB_LRS_SYNTHETIC_LAB=1`, `GIB_LRS_LAB_BASE` с числовым HTTP loopback и портом, `GIB_LRS_LAB_KEY`, `GIB_LRS_LAB_SECRET` и абсолютный `GIB_LRS_LAB_OUTBOX` с именем `gib-lrs-synthetic.sqlite`; prepare требует отсутствующий файл. Не использовать реальные учётные данные/данные пользователей. Production и внешние адреса отвергаются.

ACL, удаление, TLS, устойчивость и полноценная совместимость xAPI не подтверждены. Перед эксплуатацией нужны consent/privacy review, outbox в той же транзакции что бизнес-событие, управление ключами, retention/удаление и тестирование реального сервера.

### Проверка Ralph 5.1.0 на реальном локальном сервере

В отдельном временном Python venv установлен PyPI `ralph-malph[lrs,cli]==5.1.0` (MIT) и `requests==2.32.5` (недостающая зависимость при импорте API); сервер uvicorn привязан к 127.0.0.1, использован файловый FS backend и отдельные фиктивные Basic credentials. В `test:lrs-lab-real` выбран `GIB_LRS_LAB_ENDPOINT=ralph` (путь `/xAPI/statements`); prepare и resume с полным перезапуском сервера прошли для **одного** фиктивного statement: PUT 204, чтение, повтор 204 и изменённый объект 409. Очередь и сервер физически раздельны, данные игровой программы не использовались. После теста процессы и временные файлы удалены.

Обнаружены важные проблемы: (1) Ralph при GET с `statementId` возвращает обёртку `statements`, а не отдельный statement; тест Ralph явно проверяет этот формат, а не объявляет его совместимым со спецификацией. (2) Когда timestamp отсутствовал, Ralph добавлял новый timestamp при каждом PUT и возвращал 409 на идентичное тело. В фикстуру теперь включён **фиксированный синтетический timestamp**; версия SQLite outbox увеличена до 2, старые лабораторные файлы отвергаются, чтобы не изменить тело повтора. (3) второй новый statement в этом FS backend вернул 500: файл уже существует, операция записи создаёт файл без перезаписи. Поэтому этот backend **не годится для потока событий**, эксперимент не подтверждает работающую полноценную интеграцию. MongoDB/Elasticsearch/ClickHouse backend Ralph, параллельность, потери ответа на реальном сервере, полная спецификация xAPI и безопасность не проверены. Не применять эту конфигурацию для детей или production.
